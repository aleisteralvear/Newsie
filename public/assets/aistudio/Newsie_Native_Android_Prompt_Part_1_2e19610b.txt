REPOSITORY PRESERVATION RULE

Create the native Android implementation in a new /android project directory.

Do not delete, overwrite, or casually restructure the existing React application.

The existing application is the reference implementation. Preserve it so that its features, visual design, data models, and security requirements can be compared with the Android version.

The Android application must be independently buildable.

Build Newsie as a real native Android application.

This must not be a WebView wrapper. Do not use Capacitor, Cordova, or a WebView as the primary application interface.

Use:

- Material 3

- Room

- Android Keystore
- Android BiometricPrompt
- WorkManager

Use current stable dependency versions that are compatible with the installed Android Gradle Plugin and Kotlin versions.

Create a proper Gradle project with:

- Gradle version catalog where appropriate
- Gradle wrapper
- app/build.gradle.kts
- Android manifest

- Resource directories
- Unit tests

Use the installed Android SDK and build tools when available.

Target the latest stable Android SDK available in the environment. Use a reasonable minimum SDK, preferably API 26 or higher unless a dependency requires a different value.

Set the application name to Newsie.

Use a sensible application ID such as:
com.aleisteralvear.newsie

The final result must be a real Android APK that can be installed on a physical Android device.

5. PRIVATE WORKSPACES

This is a core feature.

Implement private workspaces as separate application-level encrypted environments.

Do not create hidden Android OS user accounts. Do not attempt to hide users from Android Settings.

A private workspace is a secure data environment inside Newsie.

Each private workspace must have its own:
- Sources.
- Categories.
- Articles.
- Bookmarks.
- Reading history.
- Search history.
- Preferences.
- Saved feed configurations.

Data from one workspace must never appear in another workspace.

5.1 WORKSPACE MANAGEMENT

Implement a private workspace dashboard.

Support:
- Create workspace.
- Select workspace.
- Unlock workspace.
- Lock workspace.
- Lock all workspaces.
- Rename workspace.
- Delete workspace.
- Change workspace passphrase.
- Change authentication method.
- Change automatic lock time.
- View workspace status.

Allow multiple private workspaces.

The dashboard must show private workspace names only after successful private dashboard authentication.

Do not expose private workspace names, IDs, or counts through normal public screens or unauthenticated interfaces.

5.2 HIDDEN ENTRY METHOD A: SEARCH PHRASE

The user can configure a private access phrase.

When the user enters this phrase into the normal Newsie search field and submits it:
1. Check the phrase locally.
2. Check it before normal search begins.
3. Do not send it to a search engine.
4. Do not save it in search history.
5. Do not save it in logs.
6. Do not save it in analytics.
7. Clear the search field immediately.
8. Open the private authentication screen if it matches.

The access phrase is an entry trigger only. It is not sufficient authentication to open private workspace data.

Require the configured workspace authentication method after the entry trigger.

Use Unicode NFC normalization.

Support spaces, punctuation, special characters, and emoji.

Retain the existing minimum passphrase policy of eight characters and maximum length of 1024 characters unless a security or platform limitation requires a documented change.

Never store the plaintext access phrase.

Store only a salted Argon2id-derived verifier.

5.3 HIDDEN ENTRY METHOD B: DOUBLE-TAP SEARCH

Implement a double-tap gesture on the Search navigation icon.

Default interval: 350 milliseconds.

Allow configuration between 200 and 800 milliseconds.

A normal single tap must continue to open Search.

A double tap must open the private authentication screen.

Support both phone navigation and larger-screen navigation.

Do not display a visible private-workspace shortcut in normal navigation.

The gesture is not authentication. It is only an entry trigger.

5.4 PRIVATE AUTHENTICATION

Support these authentication methods:
- Passphrase.
- Biometric.
- Biometric plus passphrase.

Use native Android biometric APIs.

Do not use browser WebAuthn. Do not simulate biometric authentication with a Boolean setting or device capability check.

Use:
- BiometricManager
- BiometricPrompt
- AndroidKeyStore
- AES-GCM cryptographic operations
- Authentication-bound Keystore keys

Require BIOMETRIC_STRONG for biometric-only workspace protection.

If the device does not support the required biometric security level, disable biometric enrollment and explain why.

Do not silently downgrade security.

Allow passphrase authentication as a separate supported method.

For the both method, require both factors.

Do not allow a biometric prompt alone to bypass the passphrase requirement.

Use clear fallback behavior when biometric enrollment changes or a Keystore key becomes invalidated.

The user must retain a secure passphrase recovery path.
